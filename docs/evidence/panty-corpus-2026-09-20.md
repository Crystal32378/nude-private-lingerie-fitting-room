## 四、促銷：Crystal 裁示後的定案

八件內褲頁面逐字相同：

> 至2026-10-16T00:00:00.000+00:00截止 **指定商品**，【NUDE 夏季採購折扣】一件9折，三件7折，五件5折。

### 裁示一：結束時間——採較早的一端

Crystal 說明：**官網實際檔期通常比公開規定多一些，這是常態不是錯誤。**

| 欄位 | 值 | 用途 |
|---|---|---|
| `validityEnd`（**我們主張的**） | `2026-10-15T23:59:59+08:00` | 日期比較、是否套用級距 |
| `observedSiteEnd`（**站上觀測**） | `2026-10-16T08:00:00+08:00` | 僅記錄，不參與計算 |

**採較早一端，理由是錯誤代價不對稱：**
用較晚的時間而系統其實早停 → 她結帳時折扣不在，我們承諾了沒給的錢。
用較早的時間而系統其實多跑 → 她只是少看到一次折扣宣稱。
**後者便宜得多。** 這與 v3 硬限制 fail-closed 的方向一致。

### 裁示二：「指定商品」是一條**可判定的規則**

Crystal 說明：**部分商品不列出優惠，以實際列入優惠活動的品項為準。**

這把「指定商品」從一個模糊範圍變成 per-item 的布林值——**看那件商品自己的頁面有沒有掛促銷文字。**

Schema 新增：

```ts
promotionEligible: boolean;          // 該商品頁是否掛有促銷文字
promotionEvidence: {
  text: string;                      // 逐字原文
  capturedAt: string;                // ISO 8601
  sourceUrl: string;
} | null;
```

**discount engine 只對 `promotionEligible === true` 的品項計件。** 未查證者一律視為 `false`（fail closed）。

### 裁示三：位階升為 `recorded`

活動已上線（NUDE 夏季採購折扣），不再是 `planned`。

| 欄位 | 值 |
|---|---|
| `evidenceLabel` | **`recorded`**（2026-09-20 擷取） |
| `termsVerified` | **仍為 `false`** |

`termsVerified` 不跟著升，因為仍未核對：同款多件是否分別計件、能否與會員價並用、指定清單全貌。
v3 §九「`planned` 只能是條件式模擬」的限制**解除**——`recorded` 可作為預設總額，但仍須顯示擷取時間。

**確定的部分：** 背扣「無」獨立佐證了 `closure: front`，與語料一致。

## 七、以真實價格驗算：U11 的結論要再改一次

U11 平衡點 **NT$752**。官網為兩件 fit-compatible 內衣指定的褲款是 **NT$580**——**遠低於平衡點**。

以 `nude-09`（NT$1,880）＋ p-02（NT$580）計算：

| 組合 | 件數 | 原價 | 級距 | 最終 | 每套單價 |
|---|---|---|---|---|---|
| 1 套 | 2 | 2,460 | 九折 | **2,214** | 2,214 |
| 3 件內衣 | 3 | 5,640 | 七折 | 3,948 | — |
| **3 套** | **6** | 7,380 | **五折** | **3,690** | **1,230** |

- 六件（3 套）比三件（純內衣）**便宜 258**
- 三套比一套多花 1,476，但**每套單價下降 44%**，且 3,690 落在 NT$3,000–5,000 內

> **我先前說「買更多反而便宜是雜訊不是現象」——那是錯的，因為我算的是不成套的 780 元褲款。**
> 用官網指定的 580 元成套褲款，效果是真的。
>
> 正確結論：**這個效應的符號由褲款價格決定，而成套褲款剛好落在讓它成立的那一側。**
> 所以 v3 §九的級距升級規則（預設＝她要的數量、升級只能是未勾選選項、必須顯示絕對差額）
> 不是防禦一個假想問題，而是防禦一個真實且明顯的誘因。AT-11 與 AT-14 的重要性提高。

**另一組（`nude-08` ＋ p-03）：** 2,180 ＋ 780 = 2,960 × 0.9 = **2,664**（會員價 2,910 × 0.9 = 2,619）。

**U9 結案：** 兩組 fit-compatible 套組都在 NT$3,000 以下。
v3「一套在任何合理內褲單價下都低於 NT$3,000」成立。

## 八、為什麼換掉自然順序

原規則「按分類頁自然順序」是為了防止我挑好看的商品。它在這裡失效了，原因是**官網分類頁不揭露搭配關係**——
自然順序前六件裡，官網明示的搭配內衣全都不在九件語料中，`matchingSetDesired` 整條路徑無法測試。

Crystal 指定的八件把這件事修好了，而且**修法可驗證**：這八件的 `pairsWith` 不是 Crystal 說的，
是各商品頁自己寫的「建議搭配」，**其中五件指回九件語料**，包含兩件 fit-compatible 內衣各自的對應褲款。

所以這不是為了好看而挑，是補上官網結構沒有暴露的證據。**選件依據從「順序」改為「官網明示搭配關係」，
是一條更強的規則，而且可被第三方複查。**

建議把 v3 §三的採集規則改寫為：
> 依官網明示的「建議搭配」關係選件，優先涵蓋通過穿脫檢核的內衣。
> 不得依價格或外觀挑選。每件的 `pairsWith` 必須註明出處為 `site_stated` 或 `crystal_brand_knowledge`。

## 十、範圍收斂：內褲不做試穿

**Crystal 的判斷：** 實體店本來就沒有人試穿內褲，使用者很清楚這件事，
她對內褲的擔心只有**尺寸是否合適**。成套邏輯因此很單純——
使用者同意買成套，就沿用已生成的內衣試穿圖，再放裸色商品照即可；不放也成立。
**成套只負責計算「成套更優惠」。**

### 這條收斂修正了三件事

| 原本的假設 | 修正後 |
|---|---|
| 需要內褲試穿預覽 | **不需要。** `lower_body` 探路證明可行，但產品用不到 |
| 內褲的 nude 色是 hard gate | **降為顯示用途。** 內褲不參與「白襯衫下是否顯形」判斷 |
| 顏色抓不到會擋住 deterministic gate | **不再是阻擋項。** 商品圖判讀足夠，且只用於呈現 |

同時消掉一個捏造風險：**不生成內褲影像 = 不會發明內褲構造。**

### 內褲在架構中的角色，縮到兩件事

1. **價格**（`price`、`memberPrice`、`promotionEligible`）
2. **尺寸**（站方明示的 S 32-35吋／M 36-39吋／L 40-42吋）

### 尺寸：站方對照表即為官方依據

八件商品頁一致列出：**S 32-35吋／M 36-39吋／L 40-42吋**。
**這就是官方對照表**，不需要另外的內衣尺碼換算。

```ts
pantySize: UserField<"S" | "M" | "L">;   // 由使用者從站方對照表確認
```

- 顯示站方原文對照表，**由她自己確認一個尺碼**
- 系統不推算、不建議、不從內衣尺碼換算
- 與 v3「不推算身體尺寸、不做無證據的個人化尺碼建議」一致

先前把這裡寫成「缺口」是多慮——使用者知道自己的腰臀圍，對照表是站方寫的，她確認即可。
